# Лабораторная работа №4 — Проектирование REST API

**Тема ВКР:** разработка приложения для анализа и прогнозирования значений волатильных временных рядов

## 1) Принятые проектные решения при проектировании API

### 1. Ресурсный подход (Projects, Datasets)

API разделён на ресурсы:

- `projects` — проекты (логические контейнеры для наборов данных),
- `datasets` — датасеты временных рядов, привязанные к проекту.

Каждый ресурс имеет стандартные операции CRUD и адресуется через URL:

- список: `/api/projects`, `/api/datasets`
- один объект: `/api/projects/{project_id}`, `/api/datasets/{dataset_id}`

### 2. Именование URL и использование множественного числа

Используются существительные во множественном числе: `projects`, `datasets`.  
Это соответствует REST-стилю и делает API предсказуемым.

### 3. Чёткое соответствие HTTP-методов операциям (CRUD)

Используются методы:

- `GET` — получение данных (список / один объект),
- `POST` — создание ресурса,
- `PUT` — полное обновление ресурса,
- `DELETE` — удаление ресурса.

### 4. Единый формат обмена данными (JSON)

Все запросы и ответы используют `application/json`.  
Тело запроса для `POST/PUT` передаётся в JSON, ответы также возвращаются в JSON.

### 5. Валидация входных данных через DTO (Pydantic)

Для входных данных заданы DTO-модели:

- `ProjectCreate`, `ProjectUpdate`
- `DatasetCreate`, `DatasetUpdate`

Валидация:

- `name` — строка с `min_length=1`,
- `project_id` — `PositiveInt`,
- `values` — список чисел с ограничением `min_items=2` (`conlist(float, min_items=2)`),

### 6. Ошибки и статус-коды

Приняты следующие статусы:

- `200 OK` — успешное получение/обновление,
- `201 Created` — успешное создание (`POST /projects`, `POST /datasets`),
- `204 No Content` — успешное удаление (`DELETE`),
- `404 Not Found` — ресурс не найден,
- `422 Unprocessable Entity` — ошибка валидации DTO (генерируется автоматически).

Формат ошибки — стандарт FastAPI:

```json
{ "detail": "Project not found" }
```

### 7. Связь ресурсов (Dataset принадлежит Project)

`Dataset` обязательно привязан к `Project` через поле `project_id`.  
При создании датасета проверяется существование проекта:

- если проект не найден → `404 Project not found`.

### 8. Фильтрация списка датасетов через query-параметр

Для `GET /api/datasets` реализован query-параметр:

- `project_id` (опционально)

Если параметр указан — возвращаются только датасеты данного проекта.

### 9. Каскадное удаление датасетов при удалении проекта

В `DELETE /api/projects/{project_id}` реализовано каскадное удаление:

- перед удалением проекта удаляются все датасеты, у которых `project_id == project_id`.

Это предотвращает “висячие” данные и упрощает состояние системы.

### 10. Простое хранилище в памяти для учебной версии (KISS)

Для лабораторной используется in-memory хранилище:

- `_projects`, `_datasets` (словарь `id -> объект`),
- автогенерация id через счётчики `_project_id_seq`, `_dataset_id_seq`.

Это снижает сложность (не нужна БД для демонстрации REST API).

## 2) Список эндпоинтов

### 2.1. Health

- `GET /api/health` — проверка доступности сервиса

### 2.2. Projects

- `POST /api/projects` — создать проект
- `GET /api/projects` — список проектов
- `GET /api/projects/{project_id}` — проект по id
- `PUT /api/projects/{project_id}` — обновить проект
- `DELETE /api/projects/{project_id}` — удалить проект (с каскадным удалением датасетов)

### 2.3. Datasets

- `POST /api/datasets` — создать датасет
- `GET /api/datasets` — список датасетов (опц. `?project_id=`)
- `GET /api/datasets/{dataset_id}` — датасет по id
- `PUT /api/datasets/{dataset_id}` — обновить датасет
- `DELETE /api/datasets/{dataset_id}` — удалить датасет

## 3) Описание эндпоинтов

### 3.1. `GET /api/health`

**Назначение:**  
Проверка работоспособности API. Эндпоинт используется для того, чтобы убедиться, что сервис запущен и корректно отвечает на запросы.

**Пример запроса:**  
Без тела запроса.

**Пример ответа:**
```json
{
  "status": "ok"
}
```

### 3.2. `POST /api/projects`

**Назначение:**  
Создание нового проекта. Проект выступает логическим контейнером для связанных наборов данных.

**Пример входных данных:**
```json
{
  "name": "Анализ временного ряда",
  "description": "Проект для тестирования моделей"
}
```

**Пример выходных данных:**
```json
{
  "id": 1,
  "name": "Анализ временного ряда",
  "description": "Проект для тестирования моделей"
}
```

### 3.3. `GET /api/projects`

**Назначение:**  
Получение списка всех созданных проектов.

**Пример запроса:**  
Без тела запроса.

**Пример выходных данных:**
```json
[
  {
    "id": 1,
    "name": "Анализ временного ряда",
    "description": "Проект для тестирования моделей"
  },
  {
    "id": 2,
    "name": "Прогноз продаж",
    "description": "Тестовый проект"
  }
]
```

### 3.4. `GET /api/projects/{project_id}`

**Назначение:**  
Получение информации о конкретном проекте по его идентификатору.

**Пример входных данных:**  
Идентификатор проекта передаётся в URL:
```http
GET /api/projects/1
```

**Пример выходных данных:**
```json
{
  "id": 1,
  "name": "Анализ временного ряда",
  "description": "Проект для тестирования моделей"
}
```

**Пример ошибки:**
```json
{
  "detail": "Project not found"
}
```

### 3.5. `PUT /api/projects/{project_id}`

**Назначение:**  
Полное обновление существующего проекта по его идентификатору.

**Пример входных данных:**
```json
{
  "name": "Обновлённый проект",
  "description": "Новое описание"
}
```

**Пример выходных данных:**
```json
{
  "id": 1,
  "name": "Обновлённый проект",
  "description": "Новое описание"
}
```

**Пример ошибки:**
```json
{
  "detail": "Project not found"
}
```

### 3.6. `DELETE /api/projects/{project_id}`

**Назначение:**  
Удаление проекта по идентификатору. При удалении проекта также удаляются все связанные с ним датасеты.

**Пример входных данных:**  
Идентификатор проекта передаётся в URL:
```http
DELETE /api/projects/1
```

**Пример выходных данных:**  
При успешном удалении тело ответа отсутствует, возвращается статус:
```http
204 No Content
```

**Пример ошибки:**
```json
{
  "detail": "Project not found"
}
```

### 3.7. `POST /api/datasets`

**Назначение:**  
Создание нового датасета и привязка его к существующему проекту.

**Пример входных данных:**
```json
{
  "project_id": 1,
  "name": "Ряд №1",
  "values": [10.5, 11.2, 9.8, 12.1]
}
```

**Пример выходных данных:**
```json
{
  "id": 1,
  "project_id": 1,
  "name": "Ряд №1",
  "values": [10.5, 11.2, 9.8, 12.1]
}
```

**Пример ошибки:**
```json
{
  "detail": "Project not found"
}
```

### 3.8. `GET /api/datasets`

**Назначение:**  
Получение списка всех датасетов. При необходимости можно отфильтровать датасеты по идентификатору проекта через query-параметр `project_id`.

**Пример запроса без фильтра:**
```http
GET /api/datasets
```

**Пример выходных данных:**
```json
[
  {
    "id": 1,
    "project_id": 1,
    "name": "Ряд №1",
    "values": [10.5, 11.2, 9.8, 12.1]
  },
  {
    "id": 2,
    "project_id": 2,
    "name": "Ряд №2",
    "values": [5.0, 5.5, 6.1]
  }
]
```

**Пример запроса с фильтрацией:**
```http
GET /api/datasets?project_id=1
```

**Пример выходных данных при фильтрации:**
```json
[
  {
    "id": 1,
    "project_id": 1,
    "name": "Ряд №1",
    "values": [10.5, 11.2, 9.8, 12.1]
  }
]
```

### 3.9. `GET /api/datasets/{dataset_id}`

**Назначение:**  
Получение информации о конкретном датасете по его идентификатору.

**Пример входных данных:**

**Пример выходных данных:**

**Пример входных данных:**

**Пример выходных данных:**

**Пример ошибки:**

  "detail": "Dataset not found"
